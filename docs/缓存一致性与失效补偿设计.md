# 缓存一致性与失效补偿设计

> 落地日期：2026-07-27  
> 目标：让文章、评论、搜索等核心缓存做到“主业务优先成功，缓存最终一致，失败可观测可重试”。

## 1. 解决的问题

YanBlog 现在有文章详情、热门文章、分类列表、搜索结果、评论第一页等 Redis 缓存。常规的 `更新数据库 -> 删除缓存` 能解决大多数一致性问题，但如果 Redis 短暂不可用，删除缓存失败，就可能出现较长时间读旧数据。

本次优化把缓存删除失败从“吞异常”升级为“可靠补偿任务”：

```text
业务写库成功
    ↓
事务提交后删除缓存
    ↓
Redis 删除成功：结束
Redis 删除失败：写入 cache invalidation outbox
    ↓
定时补偿任务重试删除
    ↓
成功 SUCCEEDED / 多次失败 FAILED 死信
```

## 2. 已落地能力

### 热点评论第一页缓存

- 缓存 key：`blog:article:comment:first-page:{articleId}`。
- 缓存范围：只缓存文章评论默认第一页，`pageNum=1` 且 `pageSize=10`。
- 缓存策略：复用 `CacheClient.queryWithMutex`，具备互斥重建、空值短 TTL 和随机 TTL 抖动。
- 失效时机：
  - 新增评论后失效对应文章评论第一页。
  - 文章新增、编辑、删除、上下架后失效对应文章评论第一页。

### 缓存删除失败补偿

- Interface：`CacheInvalidationRecorder`。
- Adapter：`CacheInvalidationOutboxService`。
- Outbox 表：`yan_cache_invalidation_outbox`。
- 支持能力：
  - `task_key` 唯一去重，避免同一个 key 反复刷任务。
  - `PENDING -> PROCESSING -> SUCCEEDED` 状态流转。
  - 删除失败后指数退避重试。
  - 超过最大重试进入 `FAILED`，记录死信时间。
  - 租约过期可自动恢复，避免消费者宕机导致任务永久卡住。

### 运维观测

`/api/admin/ops/outbox/summary` 已纳入 `cacheInvalidation` 统计：

- total
- pending
- duePending
- processing
- expiredProcessing
- succeeded
- failed
- processedAttempts
- maxProcessCount

`POST /api/admin/ops/outbox/retry` 会同时重放 ES、通知和缓存失效补偿任务。

## 3. 一致性边界

- 这里追求的是最终一致，不是强一致。
- 删除缓存失败不会让文章发布、评论发布、文章编辑这类主流程失败。
- Redis 恢复后，补偿任务会继续删除旧 key。
- 对搜索结果这类 pattern 缓存，当前使用 pattern 删除补偿；后续如果 key 数量继续增大，可以改成维护搜索缓存 key 索引集合，避免大范围 `keys(pattern)`。

## 4. 面试可讲亮点

可以这样说：

> 我把缓存一致性从简单的事务后删缓存升级成了可靠补偿模型。业务写库成功后再删缓存，删除失败不影响主流程，而是通过统一的 Outbox 任务记录失败 key，后台定时任务按租约锁和指数退避重试，超过次数进入死信，同时接入后台运维 summary 和一键重放。这样既保证核心业务可用性，又能让缓存最终一致，并且失败可观测、可恢复。

## 5. 后续可继续增强

1. 搜索缓存 pattern 删除改为 key registry：写搜索缓存时把 key 加入集合，失效时扫描集合删除，减少 `KEYS` 风险。
2. 为 cache invalidation 增加后台列表页：支持按 key、状态、失败原因筛选和单条重放。
3. 压测评论第一页缓存：构造热点文章评论读取 10,000 次，对比缓存前后 P95、Redis 命中率和 MySQL 查询次数。
