# YanBlog 性能优化验证记录

> 本文只记录已经在当前本地环境执行过的结果。完整压测环境、QPS、P95/P99 和错误率将在 Day 8 使用固定脚本补充。

## Day 5：评论查询与数据库索引

验证日期：2026-07-18  
环境：MySQL 8.0，本地 `yan_blog`；`yan_comment` 31 行，`yan_article` 4 行。

### 评论 SQL 数量

旧实现先查询根评论及其用户，再循环每个根评论查询直接回复，并对每个非空回复集合再查一次用户。非空页面的 SQL 数量为：

```text
3 + 根评论数 R + 存在直接回复的根评论数 C
```

最坏为 `3 + 2R`，并且使用 `to_comment_id = 根评论 ID` 会漏掉回复的回复。

新实现的非空页面固定为 4 条 SQL：

1. 根评论分页计数。
2. 根评论分页数据。
3. 使用 `root_id IN (...)` 一次查询本页全部子评论。
4. 一次查询根评论、子评论的作者及被回复用户。

真实请求：`GET /api/blog/comment/commentList?articleId=1&pageNum=1&pageSize=10`。返回 10 个根评论、总数 15；根评论 2 的子评论为 `[9, 10, 11, 16, 17]`，包含多级回复；后端日志共记录 4 条 `Preparing` SQL。

### EXPLAIN 对比

| 查询场景 | 优化前 | 优化后 | 结论 |
| --- | --- | --- | --- |
| 文章根评论分页 | `ALL`，扫描 31 行，`Using filesort` | `ref`，命中 `idx_comment_root_page`，估算 15 行，`Using index condition` | 等值过滤与时间排序由联合索引支撑 |
| 本页子评论批量查询 | `ALL`，扫描 31 行，`Using filesort` | 当前仍为 `ALL`，扫描 31 行 | 当前一次命中行占比高且表很小，优化器判断全表扫描更便宜；`idx_comment_children` 为数据增长后的按根评论查询提供访问路径 |
| 公开文章列表 | `ALL`，扫描 4 行，`Using filesort` | `ref`，命中 `idx_article_public_list`，`Backward index scan` | 状态、逻辑删除和置顶排序匹配索引 |
| 热门文章列表 | `ALL`，扫描 4 行，`Using filesort` | `ref`，命中 `idx_article_hot`，`Backward index scan` | 状态、逻辑删除和浏览量排序匹配索引 |

`yan_article_tag` 已有联合主键 `(article_id, tag_id)`，能够覆盖当前文章详情回显、标签替换和按文章删除关系的查询，因此没有重复建索引。

索引脚本见 [`docs/sql/V20260718__comment_and_article_query_indexes.sql`](sql/V20260718__comment_and_article_query_indexes.sql)。该脚本是版本化的单次迁移，不应重复执行。

## Day 13：重点优化链路高并发压测

验证日期：2026-07-22  
环境：本地后端 `http://localhost:8989`；MySQL 8.0；Redis 本地；Elasticsearch `http://192.168.25.129:9200`；k6 `v2.1.0`，安装路径 `D:\programfile\k6\k6.exe`。  
压测批次：`load_20260722_180501`。本轮压测数据按要求保留，不清理。

### 压测数据

- 新增文章：10,000 篇。
- 新增评论：10,000 条，集中挂载到压测文章，验证评论分页/批量装配链路。
- 普通作者粉丝：1,000 个。
- 大 V 作者粉丝：10,000 个。
- ES 同步 outbox：10,000 条。

脚本：

- [`scripts/load/high_concurrency_db.py`](../scripts/load/high_concurrency_db.py)：造数、投递 outbox、轮询异步结果。
- [`scripts/load/high-concurrency-http.js`](../scripts/load/high-concurrency-http.js)：k6 高并发 HTTP 压测。
- [`scripts/load/README.md`](../scripts/load/README.md)：运行说明。

### 异步链路结果

| 链路 | 规模 | 结果 | 说明 |
| --- | ---: | --- | --- |
| ES outbox 同步 | 10,000 条 | 最终全部 `SUCCEEDED` | 180 秒窗口内只完成 200 条，随后继续消费，最终查得 `SUCCEEDED:10000`、`PENDING:0`、无 `last_error` |
| 普通作者文章发布通知 | 1,000 粉丝 | 通过 | `yan_user_notification` 写入 1,000 条；由于脚本先等待 ES，本项轮询时已完成 |
| 大 V 文章发布通知 | 10,000 粉丝 | 通过 | 写入 `yan_author_publish_event` 1 条，直接通知写入 0 条，避免发布瞬间写扩散打爆数据库；由于脚本先等待 ES，本项轮询时已完成 |

ES 同步暴露出的瓶颈不是功能错误，而是当前调度配置吞吐上限偏低：默认 `blog.search.outbox.batch-size=100`、`poll-delay-ms=1000`，单实例大约每秒处理 100 条；如果前面有积压，10,000 条会明显排队。后续优化应加入分片/多 worker 并行消费、动态批量、积压监控和限流。

### HTTP 高并发结果

| 链路 | 并发/请求数 | 结果 | 失败率 | P95 | 吞吐 |
| --- | --- | --- | ---: | ---: | ---: |
| 文章详情缓存链路 | 300 VU / 10,000 次 | 通过 | 0.69% | 25.85 ms | 13,503 req/s |
| 浏览量 Redis 写入链路 | 300 VU / 10,000 次 | 通过 | 0% | 25.93 ms | 14,207 req/s |
| 评论列表批量查询链路 | 300 VU / 10,000 次 | 通过 | 0% | 515.09 ms | 725 req/s |
| ES 搜索链路 | 300 VU / 10,000 次 | 未通过 | HTTP 0%，业务检查失败 3.23% | 1,638.97 ms | 255 req/s |
| ES 搜索链路降档 | 100 VU / 10,000 次 | 通过 | 0% | 474.67 ms | 336 req/s |
| ES 搜索空结果 | 100 VU / 10,000 次 | 通过 | 0% | 442.50 ms | 431 req/s |
| ES 搜索空结果 | 300 VU / 10,000 次 | 通过 | 0% | 947.93 ms | 457 req/s |

说明：

- 文章详情首次压测出现过 4.32% 连接拒绝；脚本修正后重跑，失败率降到 0.69%，满足当前 `http_req_failed < 1%` 的验收线，但说明 300 VU 已接近本机后端连接承压边界。
- 评论列表无错误，但 P95 约 515 ms，明显慢于文章缓存和浏览量写入链路，后续可继续做评论页缓存、热点评论缓存或响应体裁剪。
- 搜索 300 VU 下 HTTP 都返回 200，但部分业务 code 非 200 且 P95 超 1.5s；100 VU 下稳定通过。当前搜索可写成“ES 搜索链路已接入并完成可靠同步，但高并发查询仍有优化空间”，不应包装成已完全抗住 300 VU。
- 不存在关键词搜索当前不走 Redis，而是直接查询 ES；100 VU 与 300 VU、各 10,000 次均通过。因此该场景不会打爆 Redis，但如果后续引入“搜索结果缓存”，必须限制空结果缓存策略，否则大量随机不存在关键词会造成 Redis key 数膨胀。

### 下一步优化方向

1. ES outbox 并行消费：把单线程定时轮询升级为可配置线程池/分片消费，按积压量动态调整批量和 worker 数，目标是让 10,000 条索引事件在固定窗口内稳定完成。
2. 搜索查询降本：增加搜索结果短缓存、热门关键词缓存、ES 查询超时/熔断、分页深度限制，减少 300 VU 下业务失败。
3. 评论读取继续优化：对热点文章评论第一页做 Redis 缓存，配合评论发布/删除时精确失效，把 300 VU 下 P95 从 500 ms 级压到 100 ms 级。
