# YanBlog 通知可靠化设计

## 目标

把评论、回复、关注这类点对点通知从“同步写收件箱”升级为“可靠任务投递”：主业务成功后，通知即使临时失败也能重试、去重、进入死信并被后台观察。

## 已落地能力

- 发文粉丝通知：继续使用 `yan_notification_outbox`，支持普通作者写扩散和大 V 作者流。
- 评论/回复/关注通知：新增 `yan_notification_delivery_outbox`。
- 收件箱 `yan_user_notification` 增加 `dedupe_key` 唯一键，保证重复投递不会产生重复通知。
- `UserNotificationService.notify(...)` Interface 保持不变，业务调用方不需要理解 Outbox。
- 发文粉丝通知和评论/回复/关注通知均已接入 Redis Stream Adapter；MySQL Outbox 继续作为可靠性源头，Redis Stream 只负责削峰和提高消费吞吐。

## Redis Stream 通知链路

### 文章发布粉丝通知

```text
文章发布主业务
        ↓
写入 yan_notification_outbox
        ↓
Outbox Relay 抢占任务并投递 yanblog:stream:notification-fanout
        ↓
notification-fanout Consumer Group 分批消费
        ↓
普通作者：按粉丝游标写扩散到收件箱
大 V 作者：写作者发布流，粉丝读取时读扩散合并
        ↓
成功 SUCCEEDED，失败指数退避 / 死信
```

### 点对点通知链路

```text
评论 / 回复 / 关注主业务
        ↓
调用 UserNotificationService.notify(...)
        ↓
写入 yan_notification_delivery_outbox
        ↓
Outbox Relay 抢占任务并投递 yanblog:stream:notification-delivery
        ↓
notification-delivery Consumer Group 消费
        ↓
INSERT IGNORE 写入 yan_user_notification
        ↓
成功 SUCCEEDED，失败重试 / 死信
```

## Redis Stream 配置

| 任务 | Stream | Consumer Group | 默认消费者数 |
| --- | --- | --- | --- |
| ES 同步 | `yanblog:stream:article-search` | `yanblog-article-search-sync` | 2 |
| 文章发布粉丝通知 | `yanblog:stream:notification-fanout` | `yanblog-notification-fanout` | 2 |
| 评论/回复/关注通知 | `yanblog:stream:notification-delivery` | `yanblog-notification-delivery` | 2 |

如果 Redis Stream 不可用或相关开关关闭，Outbox 仍可回退为定时直接处理；因此可靠性不依赖 Redis Stream，吞吐优化才依赖它。

## 幂等键

| 类型 | dedupeKey / taskKey |
| --- | --- |
| 评论通知 | `COMMENT:{commentId}` |
| 回复通知 | `COMMENT_REPLY:{commentId}` |
| 关注通知 | `FOLLOWED:{followerId}:{followeeId}` |
