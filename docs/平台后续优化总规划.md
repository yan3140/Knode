# YanBlog 平台后续优化总规划

> 整理日期：2026-07-22  
> 当前定位：YanBlog 已从基础博客项目升级为具备缓存、计数聚合、全文搜索、异步索引同步、关注通知、后台运维和压测脚本的内容平台。后续优化重点不再是“堆功能”，而是把关键业务做成可靠、可观测、可压测、可讲清的深 Module。

## 1. 当前结论

### 已经具备的能力

- 多模块 Maven 单体，`yan-admin` 为唯一后端启动入口。
- 前台/后台统一后端端口，前端页面已完成基础整合。
- 文章详情、热门文章、分类标签已接入 Redis 缓存，并处理缓存穿透、击穿、雪崩。
- 浏览量已从同步写库改为 Redis 原子计数、dirty set、定时批量落库和失败保留重试。
- 评论列表已从 N+1 查询优化为批量查询和批量用户装配。
- Elasticsearch 搜索已接入，支持中文分词、高亮、排序和文章变更后的异步索引同步。
- 文章搜索同步使用 MySQL Outbox，具备状态机、租约抢占、指数退避和手动重放。
- 关注关系、通知中心、普通作者发文通知和大 V 读扩散通知已完成基础闭环。
- 已有 k6 高并发脚本和压测报告，核心结论有数据支撑。

### 压测暴露的问题

| 链路 | 当前结果 | 暴露的问题 |
| --- | --- | --- |
| 文章详情缓存 | 300 VU / 10,000 次通过，P95 25.85 ms，失败率 0.69% | 读缓存链路性能较好，但 300 VU 已接近本机连接承压边界 |
| 浏览量 Redis 写入 | 300 VU / 10,000 次通过，P95 25.93 ms，0 失败 | 链路稳定，后续重点是监控 dirty 积压和落库延迟 |
| 评论列表 | 300 VU / 10,000 次通过，P95 515.09 ms，0 失败 | 正确性稳定，但延迟明显高于文章缓存，热点评论仍有优化空间 |
| ES 搜索命中场景 | 100 VU 通过；300 VU 未通过，P95 1.64 s | 搜索是当前最大读链路瓶颈，需要缓存、限流、降级和 ES 查询降本 |
| ES 搜索空结果 | 300 VU / 10,000 次通过，P95 947.93 ms | 当前不打 Redis；如果后续缓存搜索结果，必须防止随机空关键词制造海量 key |
| ES Outbox 同步 | 10,000 条最终成功，但 180 秒窗口内只完成少量 | 功能可靠，但吞吐受单消费者、批量大小和轮询间隔限制 |
| 发文通知 | 1,000 粉丝写扩散、10,000 粉丝读扩散均通过 | 基础模型正确，但还缺死信、单任务限制和更多故障注入测试 |

## 2. 优化原则

1. **主业务先成功，派生业务最终一致**  
   文章发布、评论、关注等主流程不应被 ES、通知、缓存删除等派生链路拖垮。

2. **重要派生业务必须可重试**  
   搜索索引、粉丝通知、评论通知、关注通知、缓存失效都应具备失败记录、重试、死信和人工补偿。

3. **高频任务必须有单任务限制**  
   同一篇文章的索引同步、同一篇文章的发文通知、同一条评论的评论通知、同一对用户的关注通知，都应有幂等键或任务键，避免重复投递。

4. **线程池只解决吞吐，不解决可靠性**  
   线程池可以提高消费速度，但不能替代 Outbox。可靠性必须由数据库任务表、状态机、租约和幂等保证。

5. **先用压测定位瓶颈，再写简历数字**  
   没有脚本、环境、数据量和原始结果支撑的性能数字不写。

## 3. 后续优先级路线

### P0：统一可靠任务 Module

目标：把 ES 同步、发文通知、评论通知、关注通知、缓存失效这些关键派生业务统一到可靠任务模型里。

落地进度（2026-07-25）：

- 已新增可靠任务规则 Module：统一任务状态、任务键生成、指数退避、最大重试和错误信息截断。
- 已将 ES Outbox 与发文通知 Outbox 接入该规则。
- 已为两张 Outbox 表增加 `task_key`、`max_retry`、`dead_letter_at`、`rerun_requested`。
- 已通过唯一 `task_key` 实现单任务限制：同一文章索引任务、同一作者同一文章发文通知不会无限重复插入待处理任务。
- 已实现重试耗尽进入 `FAILED` 死信；后台 retry 可以把 `PENDING/FAILED` 重新拉回待处理。
- 已处理任务处理中重复入队：如果任务正在 `PROCESSING`，新入队请求会标记 `rerun_requested`，当前处理完成后自动回到 `PENDING` 再跑一次，避免吞掉最后一次变更。
- 已新增迁移脚本 [`V20260725__reliable_task_outbox_hardening.sql`](sql/V20260725__reliable_task_outbox_hardening.sql)，本地 MySQL 已应用。

当前问题：

- ES Outbox 和发文通知 Outbox 已完成第一阶段统一；后续还可继续抽象为更完整的统一任务表。
- `FAILED` 死信状态已经可以进入和重放，但后台页面还可以继续加强失败任务筛选与标记处理。
- 评论通知、回复通知、关注通知还应进一步 Outbox 化。
- 缓存删除失败现在只容错，没有持久化补偿。

建议实现：

1. 建立统一任务字段：
   - `task_type`
   - `task_key`
   - `biz_id`
   - `status`
   - `retry_count`
   - `max_retry`
   - `next_retry_at`
   - `locked_until`
   - `last_error`
   - `create_time`
   - `update_time`
2. 加唯一任务键：
   - `ARTICLE_SEARCH:{articleId}`（已完成）
   - `ARTICLE_PUBLISH_NOTIFY:{authorId}:{articleId}`（已完成）
   - `COMMENT_NOTIFY:{commentId}`
   - `REPLY_NOTIFY:{commentId}`
   - `FOLLOW_NOTIFY:{followerId}:{followeeId}`
   - `CACHE_INVALIDATE:{cacheKey}`
3. 状态机升级：
   - `PENDING -> PROCESSING -> SUCCEEDED`
   - 失败时指数退避回到 `PENDING`
   - 超过最大次数进入 `FAILED`（已完成）
   - 后台可手动重放 `FAILED`（已完成）
   - 后台标记忽略（待补）
4. 运维后台增强：
   - 失败任务列表
   - 错误原因
   - 重试次数
   - 任务年龄
   - 手动重放
   - 标记已处理

简历亮点：

> 设计统一可靠任务 Module，将文章索引、粉丝通知、评论通知和缓存失效纳入事务 Outbox，支持幂等任务键、租约抢占、指数退避、死信和人工补偿，保障派生业务最终一致。

### P1：ES Outbox + Redis Stream 积压治理

目标：解决 10,000 条索引任务最终能成功但消费速度慢的问题。

当前问题：

- 单靠定时扫描 + 本地处理，吞吐主要受单实例、批量大小和 ES 写入速度影响。
- 高峰写入时 Outbox 会积压，恢复速度不够直观。
- 同一文章多次更新已经通过 `task_key` 和 `rerun_requested` 做了合并，但消费侧还需要削峰能力。
- Redis Stream 不能替代 Outbox，否则会丢掉“业务事务成功后派生任务必然可恢复”的可靠性。

已落地：

1. 不再引入独立消息队列容器，复用项目已有 Redis。
2. 基于 `spring-boot-starter-data-redis`，新增可靠任务 Redis Stream 基础配置：
   - `yanblog:stream:article-search`
   - consumer group：`yanblog-article-search-sync`
   - consumer 前缀：`yanblog-admin`
   - Stream 近似上限：`max-len=100000`
   - 搜索同步消费者数量：`consumer-count=2`
   - 已预留后续通知与缓存失效 Stream 命名：`yanblog:stream:notification-fanout`、`yanblog:stream:cache-invalidate`
3. ES Outbox 调度拆成三段：
   - `ArticleSearchOutboxService`：扫描并抢占 Outbox 任务。
   - `ArticleSearchOutboxMessageGateway`：将已抢占任务投递 Redis Stream。
   - `ArticleSearchOutboxConsumer`：消费 Redis Stream 消息后调用 `ArticleSearchOutboxProcessor` 同步 ES。
4. 当前本地配置已打开 Redis Stream：
   - `blog.reliable-task.redis-stream.enabled=true`
   - `blog.search.outbox.stream.enabled=true`
   - 关闭 Redis Stream 时仍保留原本 Outbox 本地消费兜底。
5. Redis Stream 开启后链路变为：

```text
文章发布 / 更新
        ↓
业务事务写文章 + ES Outbox
        ↓
Outbox 定时扫描并抢占任务
        ↓
Relay 投递 Redis Stream
        ↓
Consumer 消费消息
        ↓
同步 Elasticsearch
        ↓
成功 SUCCEEDED，失败按统一可靠任务策略重试 / 死信
```
6. 已补充积压与处理次数观测：
   - Outbox 统计：`pending`、`duePending`、`processing`、`expiredProcessing`、`failed`。
   - Redis Stream 统计：`streamLength`、`streamPendingCount`。
   - 业务全局唯一任务处理次数：搜索 Outbox 和通知 Outbox 均增加 `process_count`、`last_process_at`。
7. 已修复真实测试暴露的调度瓶颈：
   - Spring 默认调度线程池过小，容易被浏览量落库、通知扫描、Outbox 扫描等多个定时任务互相阻塞；已配置 `spring.task.scheduling.pool.size=4`。
   - MyBatis `StdOutImpl` 会在大批量扫描时刷出海量 SQL/结果日志，影响观察与性能；已切换为 `Slf4jImpl`，默认不再输出 SQL 明细。
   - Redis Stream Gateway 的条件装配已修正，避免开启 Stream 时误走本地 fallback。
8. 已完成一次真实链路验证：
   - 插入/重放 `ARTICLE_SEARCH:16` 任务后，Redis Stream 投递与消费成功。
   - MySQL 任务状态为 `SUCCEEDED`，`process_count=1`。
   - Redis Stream consumer group `pending=0`，说明消息已 ACK。

后续增强：

1. 增加更细的 Redis Stream Pending 治理：
   - 当前已能统计 Pending 数，并通过 MySQL Outbox 租约回收 `PROCESSING` 任务。
   - 后续可进一步接入 `XAUTOCLAIM`，专门处理“Redis 已投递但消费者崩溃未 ACK”的 Stream Pending 消息。
   - 长期失败的业务仍回落到 Outbox `FAILED`，Redis Stream 不承担最终事实状态。
2. 增加积压监控：
   - `oldest_pending_age`
   - `retry_count`
   - `batch_duration`
   - `consumer_active_count`
3. 压测验证：
   - 一次性打入 10,000 条索引任务。
   - 观察 Outbox 积压、Redis Stream 长度、Pending 数、ES 写入耗时和最终追平时间。
4. 后续通知系统复用同一个 Redis Stream 底座：
   - 发文粉丝通知
   - 评论通知
   - 回复通知
   - 关注通知
   - 缓存失效任务

验收标准：

- 一次投递 10,000 条 ES 同步任务，在固定窗口内稳定追平。
- ES 停止后任务不丢；恢复后能自动追平。
- 同一文章连续更新 100 次，最终只同步最新状态，不制造无意义重复任务。
- 关闭 Redis Stream 时应用仍可启动，并由本地 Outbox 消费兜底。
- 开启 Redis Stream 时，ES 同步任务经过 Redis Stream 消费完成。

### P2：搜索查询链路降本

目标：解决搜索 300 VU 命中场景不稳定的问题。

当前问题：

- 命中大量文章时，ES 查询、高亮、结果解析和响应体都较重。
- 100 VU 稳定，300 VU 出现业务失败和 P95 超标。
- 空结果搜索目前不打 Redis，但后续若加缓存，要防止随机 key 打爆 Redis。

建议实现：

1. 热门关键词结果缓存：
   - 只缓存热门关键词和第一页结果。
   - Key：`blog:search:result:{hash(keyword,sort,page,size)}`
   - TTL：30 秒到 2 分钟，带随机抖动。
2. 空结果短缓存：
   - 相同不存在关键词可缓存空结果。
   - TTL 要短，例如 30 秒到 120 秒。
   - 对随机关键词设置准入条件，不能无脑写 Redis。
3. 关键词准入：
   - 限制关键词长度。
   - 过滤明显随机、过长、特殊字符过多的关键词。
   - 对同一 IP 或用户做搜索频率限制。
4. ES 查询降本：
   - 默认只高亮 `title` 和 `summary`，正文高亮按需开启。
   - 限制最大 `pageSize` 和最大翻页深度。
   - 对深分页改用 `search_after` 或明确禁止。
   - `trackTotalHits` 可按业务改为上限统计，避免每次精确总数。
5. 降级策略：
   - ES 超时返回受控错误或降级到热门文章推荐。
   - 不在一次用户请求中盲目多次重试，避免放大 ES 压力。

已落地（2026-07-26）：

1. 搜索查询策略收口为 `SearchQueryPlanner` Module：
   - 默认首屏只查 5 条，前台滚动到底部再加载下一页。
   - `max-page-size=20`，`max-page-num=50`，禁止一次性大页和深分页打穿 ES。
   - `max-keyword-length=40`，明显随机长关键词不进入缓存准入。
2. ES 查询降本：
   - 默认只高亮标题、摘要、分类和标签，不再默认高亮正文。
   - `trackTotalHits` 改为阈值统计，避免每次精确统计全量命中。
3. 搜索结果缓存：
   - 只缓存第一页、较小 pageSize、通过准入的关键词。
   - 热门词需要短时间内命中至少 2 次才写入结果缓存，避免随机不存在关键词制造海量 Redis key。
   - 空结果使用更短 TTL，结果缓存带随机抖动，降低缓存雪崩风险。
4. 前台体验：
   - 搜索页从分页器改为“首屏 5 条 + 滚动加载 + 加载更多按钮兜底”。
   - 用户感知更像信息流，后端单次查询更轻。

验收标准：

- 命中场景 300 VU / 10,000 次重新压测，错误率 < 1%，P95 回到验收线以内。
- 不存在关键词 300 VU / 10,000 次仍不造成 Redis key 爆炸。
- Redis key 数、内存占用、命中率可观察。

### P3：通知系统可靠化

目标：把通知从“能用”升级为“关键业务可恢复”。

当前问题：

- 发文通知已有 outbox，但评论/回复/关注通知也应进入同一可靠模型。
- 大 V 读扩散模型已经有基础，但通知读取、未读数、删除、回复等场景还可以继续打磨。
- 重复通知和任务重复投递要用幂等键兜住。

建议实现：

1. 统一通知事件：
   - `ARTICLE_PUBLISHED`
   - `COMMENTED`
   - `REPLIED`
   - `FOLLOWED`
2. 主事务内写通知任务，不在主流程里直接完成所有通知派发。
3. 普通通知写扩散，大 V 发文读扩散。
4. 加通知幂等键：
   - 同一评论只通知一次。
   - 同一关注关系只通知一次。
   - 同一文章对同一粉丝只展示一次。
5. 通知运维能力：
   - 失败任务查询
   - 手动重试
   - 失败原因展示
   - 死信处理

已落地（2026-07-26）：

1. 新增点对点通知投递 Outbox：`yan_notification_delivery_outbox`。
   - 覆盖评论通知、回复通知、关注通知。
   - 状态机：`PENDING -> PROCESSING -> SUCCEEDED`，失败后指数退避，超过最大次数进入 `FAILED`。
   - 增加 `process_count`、`last_process_at`，用于观察单个业务通知实际处理次数。
2. 收件箱增加 `dedupe_key` 唯一键：
   - 评论/回复以 `type:commentId` 去重。
   - 关注以 `FOLLOWED:followerId:followeeId` 去重。
   - 任务重试、接口重试、消费者重复执行都不会重复写收件箱。
3. `UserNotificationService.notify(...)` Interface 不变：
   - 评论、关注业务仍调用同一个通知 Interface。
   - Implementation 已从直接写收件箱升级为可靠投递 Outbox。
4. 异步任务运维 summary 已纳入 `notificationDelivery`：
   - 可观察点对点通知的 `pending`、`processing`、`expiredProcessing`、`failed`。
   - 全部重放接口会同时处理搜索、发文通知和点对点通知 Outbox。

补充落地（2026-07-27）：

- MQ-1：文章发布粉丝通知 fanout 已接入 Redis Stream。
  - Relay 抢占 `yan_notification_outbox` 后投递 `yanblog:stream:notification-fanout`。
  - Consumer Group：`yanblog-notification-fanout`，默认 2 个 consumer。
  - 普通作者继续分批写扩散；大 V 作者继续写作者发布流，粉丝读取时读扩散合并。
  - MySQL Outbox 仍是可靠性源头，Redis Stream 只作为吞吐 Adapter；Stream 不可用时仍可回退为定时直接处理。
- MQ-2：评论、回复、关注这类点对点通知投递已接入 Redis Stream。
  - Relay 抢占 `yan_notification_delivery_outbox` 后投递 `yanblog:stream:notification-delivery`。
  - Consumer Group：`yanblog-notification-delivery`，默认 2 个 consumer。
  - 消费端按 `outboxId` 回查 MySQL 状态，只有 `PROCESSING` 任务会执行投递；重复消息会被 ACK 忽略。
  - 收件箱继续依赖 `dedupe_key` 和 `INSERT IGNORE` 保证幂等。
- 启动验证：
  - `notification-fanout` 和 `notification-delivery` 两个 Stream 均已初始化 consumer group。
  - Redis 检查结果：两个新增通知 Stream 当前 `pending=0`、`lag=0`。

验收标准：

- 评论成功但通知写入临时失败时，恢复后能补发通知。
- 同一评论接口重试不会产生重复通知。
- 大 V 发文不会直接插入海量收件箱记录。

### P4：评论读取继续优化

目标：把评论列表从“SQL 数量稳定”继续优化到“热点文章延迟稳定”。

当前问题：

- 评论列表 300 VU / 10,000 次通过，但 P95 约 515 ms。
- 响应体较大，根评论和子评论装配仍有成本。

建议实现：

1. 热点文章评论第一页缓存：
   - Key：`blog:article:comment:first-page:{articleId}`
   - 评论新增、删除、审核变化后精准失效。
2. 评论计数缓存：
   - 文章详情展示评论数时不实时 count。
3. 响应体裁剪：
   - 列表页只返回必要字段。
   - 深层回复按需展开。
4. 数据库索引复查：
   - 在 10,000+ 评论数据量下重新 `EXPLAIN`。
   - 以真实慢查询决定是否补索引。

验收标准：

- 热点文章评论第一页 300 VU 压测 P95 明显下降。
- 评论新增后缓存能及时失效或短暂最终一致。

落地结果（2026-07-27）：

- 已为文章评论第一页增加缓存：`blog:article:comment:first-page:{articleId}`，仅缓存文章评论默认第一页（pageNum=1、pageSize=10），避免深页/大页把 Redis 打成大对象缓存。
- 评论新增成功后通过 `deleteAfterCommit` 精准失效对应文章的评论第一页缓存，保证数据库事务提交后再删缓存。
- 文章新增、编辑、删除、上下架时同步失效文章详情、热门文章、分类列表、文章评论第一页以及搜索结果缓存。
- 缓存读路径继续复用 `CacheClient.queryWithMutex`，具备互斥重建、空值短 TTL 和随机 TTL 抖动，兼顾缓存击穿、穿透和雪崩风险。

### P5：缓存一致性和缓存失效补偿

目标：避免文章更新后缓存删除失败导致长时间读旧数据。

当前问题：

- `deleteAfterCommit` 能保证事务提交后再删缓存，这是正确方向。
- 但 Redis 删除失败目前只是吞异常，不会持久化记录重试。

建议实现：

1. 增加缓存失效任务：
   - 文章详情缓存
   - 热门文章缓存
   - 分类标签缓存
   - 搜索结果缓存
2. 删除缓存失败时写入任务表。
3. 定时任务重试删除。
4. 后台展示失败 key。

验收标准：

- 模拟 Redis 短暂不可用，文章更新主流程成功。
- Redis 恢复后缓存失效任务自动完成。

落地结果（2026-07-27）：

- 新增 `CacheInvalidationRecorder` Interface，`CacheClient` 删除缓存失败时不会影响主业务，而是把失败 key/pattern 写入补偿任务。
- 新增 MySQL Outbox 表 `yan_cache_invalidation_outbox`，支持 `task_key` 唯一去重、`PENDING/PROCESSING/SUCCEEDED/FAILED` 状态、租约锁、指数退避、最大重试和死信记录。
- 新增 `CacheInvalidationOutboxService` Adapter，定时扫描并重试删除 Redis key 或 pattern，Redis 恢复后能自动补偿。
- 后台异步任务运维 summary 和一键重放已纳入 `cacheInvalidation`，和 ES 同步、通知投递共用一套可靠任务观测语言。
- 数据库迁移脚本：[`V20260727__cache_invalidation_outbox.sql`](sql/V20260727__cache_invalidation_outbox.sql)，已应用到本地 MySQL。

### P6：接口限流与防刷

目标：保护搜索、评论、登录、发文、浏览量这类容易被刷的入口。

建议实现：

1. 搜索限流：
   - 用户维度
   - IP 维度
   - 不存在关键词请求特别限制
2. 评论发布限流：
   - 单用户每分钟评论数
   - 相同内容重复提交检测
3. 登录限流：
   - 用户名维度失败次数
   - IP 维度失败次数
4. 浏览量防刷：
   - 现有指纹去重基础上增加用户维度。
   - 对异常 IP 进行短期降权。

验收标准：

- 高频恶意搜索不会拖垮 ES。
- 登录爆破不会无限打数据库和 Redis。
- 评论刷屏能被限制。

落地结果（2026-07-27）：

- 新增统一限流组件：
  - `@RateLimit` / `@RateLimits` 注解用于声明接口限流规则。
  - `RedisFixedWindowRateLimiter` 使用 Redis Lua 脚本完成原子 `INCR + EXPIRE`，避免并发下计数不准。
  - `RateLimitAspect` 支持同一接口叠加多个限流维度，并在 Redis 异常时 fail-open，避免 Redis 短暂故障把主站入口全部打挂。
- 已支持的限流维度：
  - IP
  - 登录用户
  - 参数
  - IP + 参数
  - 登录用户 + 参数
- 已接入重点入口：
  - 前台搜索：IP 总量限制 + IP/keyword 限制，防止不存在关键词或同关键词高频搜索打爆 ES/Redis。
  - 评论发布：用户维度、IP 维度、用户+评论内容维度限制，防止刷屏和重复提交。
  - 前台登录：IP 维度 + username 维度限制。
  - 后台登录：更严格的 IP 维度 + username 维度限制，防止管理端爆破。
  - 浏览量接口：IP 总量限制 + IP/articleId 限制；原有 30 分钟访问指纹去重继续保留。
- 真实接口验证：
  - 临时启动后端后，对 `/api/admin/auth/login` 使用同一用户名连续错误登录 6 次，第 6 次被限流，返回 `code=429`。

边界说明：

- 当前版本是“请求尝试限流”，不是完整风控系统；登录失败次数解锁、验证码、人机校验、黑白名单可以作为后续增强。
- 固定窗口简单可靠，适合当前项目展示；如果后续要更平滑的流量控制，可升级为滑动窗口或令牌桶。

## 4. Redis Stream 演进方案

这一项已经开始作为统一可靠任务 Module 的 Redis Stream Adapter 落地。你的另一个项目已经使用 Kafka，可以展示事件流/日志型中间件能力；YanBlog 这里选择 Redis Stream，重点展示任务队列、延迟重试、死信和业务削峰的取舍能力。

### 为什么不是直接上 Kafka

YanBlog 当前的异步场景主要是任务派发，而不是海量日志流处理：

- 文章发布后同步 ES。
- 文章发布后通知粉丝。
- 评论、回复、关注后发送站内通知。
- 文章更新后清理缓存。
- 失败任务延迟重试和死信处理。

这些场景更关注“任务是否被处理、失败后如何重试、超过次数后如何进入死信”，Redis Stream 的队列、ACK、死信队列和延迟重试模型更贴近业务。Kafka 更适合事件流、日志采集、多消费者订阅和高吞吐顺序流；你可以在另一个项目里讲 Kafka，在 YanBlog 里讲 Redis Stream，能体现不是“只会一个中间件”，而是能按场景选型。

### 推荐架构

不要用 Redis Stream 替代 Outbox，而是用 Redis Stream 加速 Outbox：

```text
文章发布 / 评论 / 关注 / 缓存失效
        ↓
主事务写业务表 + Outbox 任务表
        ↓
Outbox Relay 投递 Redis Stream
        ↓
Redis Stream Consumer 消费消息
        ↓
ES 同步 / 通知派发 / 缓存删除
        ↓
成功标记 SUCCEEDED，失败指数退避或进入死信
```

关键点：

- MySQL Outbox 负责可靠性：应用崩溃、Redis Stream 短暂不可用时任务不丢。
- Redis Stream 负责削峰和吞吐：Consumer Group 可以分摊消费压力，比单机定时扫描更灵活。
- 定时扫描保留为兜底：Relay 漏投、Redis Stream 不可用或消息丢失时，仍可从 Outbox 表恢复。
- 消费端必须幂等：同一任务重复投递不能造成重复通知、重复索引或重复缓存操作。

### 当前最小落地方案

当前先用 P1 的 ES 同步作为第一条 Redis Stream 链路：

1. 已引入 `spring-boot-starter-data-redis`。
2. 定义业务 Stream 和 Consumer Group：
   - `yanblog:stream:article-search`
   - `yanblog-article-search-sync`
3. 文章发布、评论、关注等主流程仍然只写业务表和 Outbox，不直接依赖 Redis Stream。
4. 已新增 ES Outbox Relay：
   - 扫描 `PENDING` 任务。
   - 抢占后发送 Redis Stream。
   - 发送失败时按统一可靠任务策略重试。
5. 已新增 ES Redis Stream Consumer：
   - 根据 `outboxId` 查询任务。
   - 校验状态。
   - 调用 `ArticleSearchOutboxProcessor` 执行业务处理。
   - 成功标记 `SUCCEEDED`。
   - 失败则更新 `retry_count`、`next_retry_at`、`last_error`。
6. 保留现有本地处理作为兜底，Redis Stream 总开关关闭时不影响开发启动。

这个版本的优势是改动可控，不会破坏当前已经完成的 Outbox 可靠链路。

### 标准可靠方案

如果后面想继续加深，可以升级为完整可靠任务体系：

1. 统一任务表或统一任务 Interface。
2. 增加 `task_key` 单任务限制。
3. 增加 `max_retry` 和 `FAILED` 死信终态。
4. Redis Stream 使用 Pending List + 超时认领实现消费恢复；延迟重试仍以 MySQL Outbox 的 `next_retry_at` 为准。
5. 后台可查看：
   - 待投递任务
   - 消费中任务
   - 重试任务
   - 死信任务
   - 最后错误原因
6. 后台支持：
   - 手动重放
   - 标记忽略
   - 按任务类型筛选
   - 按业务 ID 查询任务链路

### 面试表达

可以这样讲：

> 当前项目已经实现 MySQL Outbox，保证文章索引和粉丝通知这类派生任务不会因为应用重启或 ES 故障丢失。在此基础上，我复用项目已有 Redis，引入 Redis Stream 作为可靠任务 Module 的轻量队列 Adapter：Outbox 负责可靠落库，Redis Stream 负责削峰和提高消费吞吐，消费者通过幂等任务键、Consumer Group、ACK、Pending 消息恢复和死信状态保障最终一致。另一个项目使用 Kafka 处理事件流，YanBlog 这里选择 Redis Stream 是因为它更轻量、更贴合单体博客项目。

### 简历可选表达

如果继续完成压测后，可以写：

如果暂时只作为设计方案，可以写得更克制：
