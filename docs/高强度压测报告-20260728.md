## 6. 本轮发现的 P1 问题

### P1-1：通知投递 Outbox 假成功

现象：

- `yan_notification_delivery_outbox`：10000 条全部 `SUCCEEDED`
- `yan_user_notification`：实际只新增 100 条

根因：

- `yan_user_notification` 存在唯一键：`(receiver_id, article_id, type)`
- 同一个用户在同一篇文章下收到多条评论通知时，后续通知被 `INSERT IGNORE` 静默忽略
- 服务层未校验 `insertIgnore` 返回行数，导致业务数据没有落库但 Outbox 被标记成功

建议：

- 删除或调整 `uk_notification_article_receiver` 唯一键，幂等唯一性应以 `dedupe_key` 为准。
- `insertIgnore` 必须检查返回行数：如果插入 0 行，需要确认是否已存在相同 `dedupe_key`；否则应该进入重试/死信。

### P1-2：后台异步任务依赖登录态

现象：

- 通知 fanout 消费线程出现 `SecurityUtils.getAuthentication() == null`
- MyBatisPlus 自动填充在后台线程中尝试读取当前登录用户，导致 NPE

建议：

- 后台任务线程不要依赖登录态。
- 自动填充处理器对无登录上下文场景提供系统用户兜底，例如 `0` 或固定系统用户 ID。

### P1-3：ES 同步消费者吞吐不足

现象：

- 10000 条 ES 同步任务 240 秒内仅完成 238 条。
- 后续观测仍有大量 PENDING/PROCESSING。

判断：

- 当前消费者更像单条处理/小批量处理，无法承受万级突发写入。

建议：

- Redis Stream 消费侧按批处理事件，并使用 ES Bulk API 批量写入。
- 增加消费者数量、批大小和每批最大等待时间配置。
- 增加队列积压监控：pending 数、processing 数、失败数、最长等待时间。

## 7. 后续优化优先级

1. 先修通知投递正确性：唯一键 + `INSERT IGNORE` 假成功校验。
2. 修后台任务登录态依赖：自动填充支持系统线程。
3. 优化 ES 同步吞吐：批量消费 + Bulk API + 积压监控。
4. 调整高并发启动瞬间连接拒绝：Tomcat `accept-count`、线程池、连接队列和压测 ramp-up 策略。
5. 搜索命中链路补充错误码采样：k6 脚本记录非 200 业务码分布，避免只看到总体失败率。

## 8. 本轮优化处理记录

已完成本轮压测发现的 5 项优化：

- 通知投递正确性：`NotificationDeliveryOutboxService` 已校验 `insertIgnore` 返回值；插入 0 行时，只有确认 `dedupe_key` 已存在才标记成功，否则进入可靠任务重试。
- 通知表唯一键：新增迁移脚本 `docs/sql/V20260728__fix_notification_dedupe_unique_key.sql`，将错误唯一键 `uk_notification_article_receiver(receiver_id, article_id, type)` 调整为普通索引，通知幂等统一由 `dedupe_key` 负责。
- 后台任务登录态：`MyMetaObjectHandler` 已对无登录上下文的后台任务使用系统用户 `0` 兜底，不再打印异常堆栈。
- ES 同步吞吐：`ArticleSearchOutboxConsumer` 已从逐条调用 Processor 改成批量 claim 后一次性批处理；默认 Stream 消费配置调整为 `consumer-count=4`、`consumer-batch-size=200`、`poll-delay-ms=100`。
- 峰值连接拒绝：Tomcat 增加 `accept-count=1000`、`max-connections=10000`、`threads.max=400`、`threads.min-spare=50`，降低瞬时高并发直冲时连接被拒绝的概率。
- 压测可观测性：k6 脚本增加 `business_failures` 自定义计数器，按 `endpoint/status/code` 记录业务失败分布，后续不用只看总体失败率。
