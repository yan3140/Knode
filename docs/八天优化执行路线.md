# YanBlog 八天优化执行路线

> 目标：八天内将 YanBlog 从基础博客项目升级为可验证的高性能内容平台。先补齐后台文章创作闭环，再完成“工程可信度 → 热点读缓存 → 高频计数写入 → 搜索异步同步 → 观测压测”；不在本周期引入 AI/RAG。

> 进度更新（2026-07-19）：Day 1、Day 3、Day 4、Day 5、Day 6、Day 7 已完成并通过回归；Day 2 的 Maven 多模块、单启动类、认证边界、API 命名空间和前端登录衔接已完成，配置脱敏、README 与本地运行手册按当前取舍暂缓。后续 Day 8 的事务 Outbox 最小闭环也已完成，详情见 [`docs/后续优化路线.md`](后续优化路线.md)。

## 最终交付

- 可复现的本地运行环境与脱敏配置。
- 文章详情、热门文章、分类标签的 Redis 缓存治理。
- 浏览量的 Redis 原子计数、dirty set、批量持久化与防刷。
- 评论列表 N+1 查询优化。
- Elasticsearch 全文搜索与文章变更后的异步索引同步。
- 核心单元/集成测试、k6 脚本、性能报告和监控指标。

## 完成边界

本周期只使用多模块单体架构；不拆微服务，不同时引入 Kafka、向量数据库和 AI。Redis Stream 队列优先选择 Redis Stream；若时间不足，先以事务后事件 + 失败补偿实现索引同步，并在文档中说明后续可替换为 Redis Stream。

## Day 1：补齐后台文章创作与管理闭环

状态：已完成。

### 工作项

1. 新增后台文章分页列表接口，支持标题、状态、分类等必要筛选。
2. 新增文章详情接口，用于编辑页回显文章内容、分类和已关联标签。
3. 新增编辑文章接口；更新文章时先校验数据，再在同一事务内替换文章标签关联。
4. 新增删除、下架、草稿保存、发布/撤回等状态流转接口；前台只展示已发布且未删除的文章。
5. 为新增、编辑请求建立校验：标题、正文、摘要、分类、状态、标签集合；校验分类和标签存在且可用。
6. 为新增、编辑、删除操作添加 `@Transactional`，保证文章与标签关联原子提交。
7. 修正后台匿名登录路径；对文章管理接口增加明确的权限标识或最小角色校验。
8. 补文章新增、编辑、标签替换、状态变更和事务回滚测试。

### 验收

- 管理员可完成“草稿 → 编辑 → 发布 → 下架/删除”的完整流程。
- 编辑文章后，分类、正文和标签关联均与请求一致，不保留旧标签。
- 标签写入失败时，文章主记录不会被半提交。
- 前台列表、热门列表和详情均不会暴露草稿、下架或已删除文章。

## Day 3：文章阅读缓存

状态：已完成。

验证记录：文章详情、热门列表、分类列表首次请求查询 MySQL，第二次请求 SQL 数量为 0；不存在文章使用 2 分钟空值缓存；正常缓存 TTL 带随机抖动。后台文章状态变更后详情、热门和分类缓存失效，标签更新后标签缓存失效。

### 工作项

1. 为文章详情引入 `blog:article:detail:{id}` 缓存，缓存 `ArticleDetailVo`。
2. 实现缓存空值、随机 TTL 和互斥锁重建；锁必须含过期时间与 `finally` 释放保护。
3. 后台新增、修改、删除或上下架文章时主动失效详情缓存。
4. 缓存热门文章列表 `blog:article:hot:list`，并在内容变更后失效或刷新。
5. 缓存分类、标签列表；对应后台变更时失效。

### 验收

- 覆盖缓存命中、未命中、空值、锁竞争和失效的测试。
- 热点详情重复请求不重复查询 MySQL。
- Redis 不可用时接口可降级回源或返回明确的受控错误，不出现空指针。

## Day 4：浏览量计数可靠化

状态：已完成。

验证记录：40 个不同访问指纹并发请求精确增加 40，同一指纹并发重复 10 次只增加 1；不存在文章不创建计数。Redis 计数 156、MySQL 旧值 115 时强制重启，启动初始化保留 Redis 新值；一分钟批量任务随后将 MySQL 更新为 156，并在成功后清空 dirty 标记。数据库更新异常的单元测试验证 dirty 标记不会被移除。

### 工作项

1. 抽出 `ArticleCounterService`，统一隐藏浏览量的 Redis 与落库逻辑。
2. 使用 `blog:article:view-count` Hash 保存计数，使用 `blog:article:view-count:dirty` Set 标记待同步文章。
3. 访问时使用原子 `HINCRBY` + `SADD`；用指纹 Key 与 TTL 限制同一访问者短时间重复计数。
4. 定时任务分批处理 dirty articleId；数据库成功后才移除 dirty 标记，失败保留以便重试。
5. 调整启动加载逻辑，避免覆盖 Redis 中尚未持久化的计数；增加关闭前尽力刷盘。

### 验收

- 并发增加同一文章浏览量，计数准确。
- 数据库故障后 dirty 标记仍存在，恢复后可补偿成功。
- 不存在文章不会产生无效计数。

## Day 5：评论查询与数据库优化

状态：已完成。

验证记录：文章 1 的评论第一页实际返回 10 个根评论，根评论 2 的子评论完整包含 `[9, 10, 11, 16, 17]`；一次非空评论列表请求固定执行 4 条 SQL。根评论、公开文章列表和热门文章查询均命中新索引；子评论查询在当前 31 行小表上仍由优化器选择全表扫描，原因与执行计划已如实记录在 `docs/性能优化验证报告.md`。

### 工作项

1. 将“每个根评论查询一次子评论”改为一次批量查询全部子评论，再在内存中按 rootId 分组。
2. 批量查询根评论和子评论涉及的用户，统一填充昵称，避免用户查询 N+1。
3. 梳理文章、评论、文章标签表上的高频查询条件，为状态、文章 ID、根评论/回复关系等补充必要索引。
4. 使用 `EXPLAIN` 记录优化前后执行计划，并将结论写入性能报告。

### 验收

- 一个评论列表页的 SQL 数量不随根评论数线性增长。
- 评论树结构、排序和用户昵称保持正确。
- 为新增索引说明对应查询场景，而非盲目建索引。

## Day 6：全文检索与索引同步

状态：已完成。

验证记录：虚拟机 Docker 已升级为 Elasticsearch 9.4.3 与官方 SmartCN 9.4.3 插件，项目同步升级为类型安全的 Java API Client 9.4.3，REST 5 Client 仅保留为内部传输层；使用独立新卷并从 MySQL 重建 3 篇已发布文章，旧 7.12.1 容器和卷保留回退。中文搜索、高亮、分页以及相关度/最新/热度排序均通过真实接口验证；文章更新、下架、重新发布能够在事务提交后异步反映到 ES。ES 停止时失败 ID 进入 Redis，重启后补偿成功并清空标记。设计与证据见 `docs/搜索设计.md`。

### 工作项

1. 复用虚拟机 Docker 中的 Elasticsearch，定义文章索引 Mapping 与初始化/重建命令。
2. 新建搜索模块接口，支持标题、摘要、正文、分类、标签多字段搜索；标题权重最高。
3. 返回高亮、分页，并支持相关度、最新、热度排序。
4. 文章发布、更新、删除、上下架后发送文章变更事件，由异步消费者更新或删除索引。
5. 为同步失败保留重试与后台补偿接口；MySQL 始终作为事实来源。

### 验收

- 发布、更新、删除/下架均能在搜索结果中正确反映。
- ES 故障不阻塞文章发布主流程，失败事件可发现并补偿。
- 可以按文章 ID 及全量重建索引。
