# YanBlog 文章全文搜索设计

## 完成边界

Day 6 使用虚拟机 Docker 中的 Elasticsearch 9.4.3，不引入 Docker Compose 或新 Maven 模块。MySQL 始终是文章事实来源，Elasticsearch 只保存可公开搜索的已发布文章。后续 P1 已在统一可靠任务 Module 后增加 Redis Stream Adapter，用于 ES Outbox 的削峰和并发消费。

项目使用与服务端同版本的官方 Java API Client 9.4.3，业务仓库通过类型安全的 Java DSL 调用建索引、Index、Bulk、Search、Delete 和 Delete By Query API；REST 5 Client 只作为 Java API Client 内部传输层，不再由业务代码拼接请求 JSON。中文及中英文混合内容使用同版本的 Elastic 官方 `analysis-smartcn` 插件，不再依赖第三方 IK 插件。

原 Elasticsearch 7.12.1 容器保留为停止状态的 `es-7-backup`，原 `es-data`、`es-plugins` 卷均未修改。9.4.3 使用独立的 `yanblog-es-9-data`、`yanblog-es-9-plugins` 卷，然后从 MySQL 全量重建业务索引；没有跨大版本直接复用旧数据目录。

## 索引 Mapping

索引名：`yan_blog_articles`  
分片：1 个主分片、0 个副本。当前是单节点开发环境，0 副本可使该业务索引保持 `green`。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `id` | `long` | 文章 ID，也是 ES 文档 `_id` |
| `title` | `text` | SmartCN 中文/中英文分词，搜索权重 5 |
| `summary` | `text` | SmartCN 分词，搜索权重 3 |
| `content` | `text` | SmartCN 分词，搜索权重 1 |
| `categoryId` | `long` | 分类 ID |
| `categoryName` | `text` | SmartCN 分词，搜索权重 2 |
| `tagNames` | `text` | 标签名集合，SmartCN 分词，搜索权重 2 |
| `thumbnail` | `keyword` | 只随结果返回，不参与索引 |
| `viewCount` | `long` | 热度排序 |
| `createTime` | `date/epoch_millis` | 最新排序 |

索引只保存已发布且未逻辑删除的文章，因此查询不需要再维护一份状态过滤条件。

## 搜索接口

公开接口：

```text
GET /api/blog/search?keyword=Spring&pageNum=1&pageSize=10&sort=relevance
```

`sort` 支持：

- `relevance`：相关度优先，发布时间作为次级排序。
- `latest`：发布时间优先，相关度作为次级排序。
- `hot`：浏览量优先，相关度作为次级排序。

响应使用统一 `PageVo`，每条数据包含标题、摘要、分类、标签、浏览量、创建时间、分数以及 `title/summary/content/categoryName/tagNames` 的高亮片段。分页大小最大为 50，空关键词或非法排序返回参数错误。

## 同步与补偿（Day 8 Outbox）

```text
文章变更 / 浏览量批量落库
        ↓ 同一 MySQL 事务写入 yan_article_search_outbox
PENDING 事件持久化
        ↓
定时消费者原子抢占为 PROCESSING（带租约）
        ↓
重新读取 MySQL 当前状态
   ├─ 已发布：重新组装分类/标签并覆盖 ES 文档
   └─ 草稿、下架、删除：删除 ES 文档
        ↓
成功：标记 SUCCEEDED
失败：回到 PENDING，记录 retryCount、lastError、nextRetryAt
        ↓
固定延迟自动重试，也可由后台手工提前重放
```

Outbox 表为 `yan_article_search_outbox`，每次文章变更都新增一条事件，不依赖 JVM 内存事件或 Redis 失败集合。文章新增、编辑、上下架、删除，以及浏览量 dirty set 成功刷入 MySQL 后，都会在对应 MySQL 事务中写入事件。消费者始终按 article ID 读取 MySQL 当前状态；ES 文档 ID 固定为文章 ID，因此重复 upsert/delete 是幂等的，连续编辑最终会收敛到最新状态。

Day 9 将消费者升级为批处理：每轮最多读取 100 个待处理事件，并逐条条件抢占，避免多实例重复消费；按文章 ID 去重后一次读取 MySQL，通过一次 ES Bulk 请求同时 upsert 已发布文章、delete 草稿/下架/删除文章。Bulk 响应中的单条失败只会重试对应文章事件，成功事件立即完成。

失败等待采用指数退避：10 秒、20 秒、40 秒……最大 300 秒；事件保留 `retryCount`、`lastError` 与 `nextRetryAt`。`blog.search.outbox{result=success|failure}` 记录每批完成和重试的事件数量。

2026-07-25 已补充统一可靠任务规则：搜索 Outbox 增加 `task_key`、`max_retry`、`dead_letter_at` 和 `rerun_requested`。同一文章使用 `ARTICLE_SEARCH:{articleId}` 作为幂等任务键；如果任务已在 `PENDING/FAILED/SUCCEEDED`，再次入队会复用同一任务并拉回 `PENDING`；如果任务正在 `PROCESSING`，再次入队会标记 `rerun_requested`，当前处理完成后自动回到 `PENDING` 再处理一次，避免连续编辑吞掉最后一次变更。重试次数达到 `max_retry` 后进入 `FAILED` 死信，后台 retry 可重新拉起。

2026-07-25 P1 已补充 Outbox + Redis Stream 链路：`ArticleSearchOutboxService` 仍负责扫描、租约抢占和本地兜底；当 `blog.reliable-task.redis-stream.enabled=true` 且 `blog.search.outbox.stream.enabled=true` 时，已抢占任务会通过 `ArticleSearchOutboxMessageGateway` 投递到 `yanblog:stream:article-search`，由 `ArticleSearchOutboxConsumer` 消费后调用 `ArticleSearchOutboxProcessor` 同步 ES。Redis Stream 只负责削峰和消费吞吐，可靠性仍由 MySQL Outbox、`task_key`、重试和死信状态承担。

2026-07-26 已将本地 Redis Stream 打开并验证真实链路：Stream 使用近似上限 `max-len=100000`，搜索同步配置 `consumer-count=2`，后台 summary 可查看 `streamLength`、`streamPendingCount`、`processedAttempts` 和 `maxProcessCount`。`yan_article_search_outbox` 增加 `process_count`、`last_process_at`，每次 Processor 真正处理业务任务前自增处理次数；通知 Outbox 也补充同字段，便于后续发文通知、评论通知、回复通知、关注通知接入同一 Redis Stream 底座后统一观测。当前已实测 `ARTICLE_SEARCH:16` 从 Outbox 投递到 Redis Stream 后消费成功，任务状态 `SUCCEEDED`，处理次数为 1，consumer group pending 为 0。

真实测试时还发现并修复两个工程问题：第一，Spring 默认调度线程池会让多个定时任务互相排队，Outbox relay 在大批量扫描时可能被拖慢，已配置调度线程池大小为 4；第二，MyBatis `StdOutImpl` 在大数据量扫描时会刷出海量 SQL 和结果日志，已切换为 `Slf4jImpl`，避免日志本身成为压测干扰项。

2026-07-26 P2 已补充查询链路降本：公开搜索默认首屏只取 5 条，前台滚动加载后续结果；后端限制 `max-page-size=20`、`max-page-num=50`，避免一次性大页和深分页。ES 查询默认关闭正文高亮，只保留标题、摘要、分类和标签高亮；`trackTotalHits` 使用阈值统计。第一页小结果集接入 Redis 缓存准入，热门词短时间内重复访问才缓存结果，空结果使用更短 TTL，避免随机不存在关键词把 Redis 打爆。

后台接口：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/admin/content/search/sync/{articleId}` | 按 MySQL 当前状态同步单篇文章 |
| `POST /api/admin/content/search/retry` | 将全部 `PENDING` Outbox 事件设为立即可执行，等待调度器处理 |
| `POST /api/admin/content/search/rebuild` | Bulk 覆盖全部已发布文章，并删除 MySQL 中已不存在的脏文档 |

全量重建不会删除再创建整个索引，而是先 Bulk 覆盖当前文章，再用 `_delete_by_query` 清理不在当前 ID 集合中的文档，避免重建期间索引短暂不存在。

## 故障边界

- ES 不可用不会回滚已经提交的文章事务；公开搜索返回受控错误 517。
- Outbox 与文章写入在同一 MySQL 事务提交，应用在提交后崩溃时，未完成事件仍保留在数据库；过期租约会被后续调度器回收。
- 当前实现是至少一次语义；ES 写入必须保持幂等。Redis Stream 开启后负责削峰与并发消费，Redis Stream 关闭或不可用时仍保留本地 Outbox 消费兜底。
- 全量重建仍保留为灾难恢复工具，不承担日常失败补偿。
