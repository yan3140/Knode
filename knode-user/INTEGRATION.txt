G3-USER-03 integration notes
Public routes implemented: POST /api/blog/auth/login, POST /api/admin/auth/login, POST /api/blog/user/register, GET/PUT /api/blog/user/userInfo, GET /api/admin/auth/me, GET /api/admin/auth/routers, POST /api/blog/auth/logout and POST /api/admin/auth/logout. Other old aliases are not implemented in this slice.
Use env.example as a variable template after replacing placeholders; use a dedicated, isolated MySQL database and Redis instance. Set exactly one of KNODE_AUTH_SIGNING_PRIVATE_FILE and KNODE_AUTH_SIGNING_PRIVATE_ENV (the latter names a separate variable containing PKCS#8 PEM). KNODE_AUTH_SIGNING_PUBLIC_FILE is X.509 PEM. No production key is generated.
Apply src/main/resources/db/schema.sql only in a separately authorized new user database. spring.sql.init.mode=never; the application does not apply DDL, create accounts, or migrate old data.
Runtime database privileges: SELECT on sys_user, sys_role, yan_menu, sys_user_role, sys_role_menu and auth_revocation_intent; INSERT on sys_user and auth_revocation_intent; UPDATE on sys_user and auth_revocation_intent. A read-only account alone cannot support registration, profile updates or logout. Obtain a sanitized structure and migration plan from the controller before importing legacy data, including uniqueness collisions, ID preservation, deletions and MySQL collation.
Redis read and write factories use separate KNODE_AUTH_REDIS_READ_* and KNODE_AUTH_REDIS_WRITE_* settings and TLS defaults to true. Restrict the reader to GET and the user writer to SET with NX/expiry and DEL on knode:<environment>:v1:auth:session:*. Do not pipeline or transact GET; null must mean missing. ACL isolation and connectivity have not been verified against an actual Redis server.
GET /health/live is process liveness. GET /health/ready checks required database tables, tests intent INSERT/UPDATE in a rolled-back transaction, exercises database UPDATE privileges and probes auth Redis read and write with an expiring temporary key. It does not validate every CRUD privilege, true ACL isolation or event delivery.
The normal request filter independently verifies the token and authoritative session, checks pending sid revocation and current database account state, then enforces route scope. It rejects repeated/merged token headers and spoofed identity headers. Production has no in-memory session configuration.
Logout commits a PENDING sid intent before deleting the Redis session, then atomically marks it REVOKED and inserts a separate PENDING outbox fact. Redis failure returns 503; the same valid sid can retry logout without logging in again. Other requests for PENDING sid return 503. A scheduled bounded worker retries with expiring leases and exponential delay (2 to 300 seconds); an individual failure does not stop the rest. KNODE_AUTH_REVOCATION_POLL_MS and KNODE_AUTH_REVOCATION_INITIAL_MS configure timing. Protected metrics require system:revocation:monitor. Stream Relay and Agent pause are not implemented: a REVOKED row or PENDING outbox record is not proof of delivery. Repeated use of an already-revoked token returns 401.
H2 MySQL-mode HTTP tests use generated keys and Redis session-port substitutes; this is not MySQL, Redis, ACL, Gateway or end-to-end cross-service validation.

G4: Apply V004__rbac_revocation.sql only after separately authorized migration of a G3 user database; new databases use updated schema.sql. Existing G3 sid records are absent from auth_login_session. Plan a controlled cutover: user service rejects those tokens, but gateway/other services can still accept them until expiry. Stop G3 token issuance before waiting the maximum token TTL, or retire the old verification key in every verifier in a coordinated cutover. Do not perform that cutover automatically.
Runtime database account needs SELECT/INSERT/UPDATE/DELETE only on the user-domain tables as needed, plus SELECT/UPDATE on user_security_lock; no DDL privileges are required. Management mutations acquire its singleton row lock and re-read permissions; user 1, role 1, roles with reserved core keys admin/super_admin/superadmin, their assigned users and menus cannot be altered through management endpoints. The last active administrator with system:user:edit or *:*:* is protected. Admins cannot edit their own account through management endpoints, and cannot assign roles or menu privileges they do not already hold unless they possess the database-granted wildcard. Reserved role keys admin, super_admin and superadmin cannot be created or assigned via role editing.
The session index enables password reset and account changes to enqueue and attempt per-sid Redis revocation after database commit. An HTTP 503 may mean the database mutation committed but authority revocation is still pending; clients must not blindly retry as if no change occurred. Login sessions, intents and outbox rows currently have no cleanup or Stream delivery policy; retention and consumer contracts require a later task.

Historical G3 intents already marked REVOKED predate auth_revocation_outbox and are not automatically backfilled. Their event IDs and timestamps remain in the intent table, but they will not be published unless the controller separately approves a backfill/replay plan. G4 does not claim historical events were delivered.
