G2-USER-02 integration notes: AUTH-USER/SESSION v0.2 semantic revision approved by controller; cross-service integration pending.
com.lx:knode-auth is CPU-only. Construct UserTokenVerifier with trusted RS256 kid/public key map and Clock. Call verifyToken(token), perform an authoritative async Redis GET using the returned sid, decode with SessionCodec.decode and call validateSession(verified, Optional<Session>, requiredScope). Map malformed state/transport failure to 503, missing or invalid session to 401, valid session with insufficient scope to 403. Do not check scope before reading and validating the session. Never cache positive session results.
The user service owns the signer and private key. Credential verification and active-account eligibility must precede issue; no login HTTP endpoint exists. Keys must be externally injected via environment or secure local files, never embedded in source.
RedisSessionReader and RedisSessionWriter accept distinct StringRedisTemplate instances, allowing separate endpoint, port and credential configuration, and an environment name for the isolated key namespace. The reader must use a Redis account restricted to GET; the user writer account requires SET with NX/expiry and DEL only on its auth prefix. SessionRedisConnections.create(System.getenv(), prefix) creates separate connection factories using KNODE_AUTH_REDIS_READ_ and KNODE_AUTH_REDIS_WRITE_ plus HOST, PORT, USERNAME, PASSWORD, optional DATABASE and TLS (default true); initialize and wrap each factory in its own StringRedisTemplate. Use KeyMaterial.privateFromEnvironment or privateFromFile and publicFromFile for key injection. Do not pipeline or transact session GET: null must mean missing, not an uncompleted pipeline result. No default credentials or implicit production session configuration is supplied. Redis connections, ACLs, TLS, and topology remain deployment responsibilities and are not tested here.
UserAuthenticationFilter requires explicit registration on protected routes; it rejects multiple/merged token headers and external X-Internal-*, X-User-*, X-Principal-*, X-Service-*, X-Identity-*, X-Authenticated-*, X-Forwarded-User, X-Remote-User and X-Auth-Request-User headers, validates identity directly, and does not enforce resource ownership. Confirm the internal-header list with ingress before integration.
No database credential verification, durable revocation intent/outbox, event propagation, service/delegation token issuance, key distribution endpoint or cross-service integration exists in this slice. Revoking an already invalid HTTP token returns 401; Redis writer DEL is idempotent by sid. A timeout after a write has uncertain outcome: reconcile state rather than assuming failure means no effect.
