G3-USER-03 integration notes
Public routes implemented: POST /api/blog/auth/login, POST /api/admin/auth/login, POST /api/blog/user/register, GET/PUT /api/blog/user/userInfo, GET /api/admin/auth/me, GET /api/admin/auth/routers, POST /api/blog/auth/logout and POST /api/admin/auth/logout. Other old aliases are not implemented in this slice.
Use env.example as a variable template after replacing placeholders; use a dedicated, isolated MySQL database and Redis instance. Set exactly one of KNODE_AUTH_SIGNING_PRIVATE_FILE and KNODE_AUTH_SIGNING_PRIVATE_ENV (the latter names a separate variable containing PKCS#8 PEM). KNODE_AUTH_SIGNING_PUBLIC_FILE is X.509 PEM. No production key is generated.
Apply src/main/resources/db/schema.sql only in a separately authorized new user database. spring.sql.init.mode=never; the application does not apply DDL, create accounts, or migrate old data.
Runtime database privileges: SELECT on sys_user, sys_role, yan_menu, sys_user_role, sys_role_menu and auth_revocation_intent; INSERT on sys_user and auth_revocation_intent; UPDATE on sys_user and auth_revocation_intent. A read-only account alone cannot support registration, profile updates or logout. Obtain a sanitized structure and migration plan from the controller before importing legacy data, including uniqueness collisions, ID preservation, deletions and MySQL collation.
Redis read and write factories use separate KNODE_AUTH_REDIS_READ_* and KNODE_AUTH_REDIS_WRITE_* settings and TLS defaults to true. Restrict the reader to GET and the user writer to SET with NX/expiry and DEL on knode:<environment>:v1:auth:session:*. Do not pipeline or transact GET; null must mean missing. ACL isolation and connectivity have not been verified against an actual Redis server.
GET /health/live is process liveness. GET /health/ready probes JDBC SELECT 1 and auth session read; it does not verify write ACL, schema correctness, or event delivery and must not be treated as proof that writes work.
The normal request filter independently verifies the token and authoritative session, checks pending sid revocation and current database account state, then enforces route scope. It rejects repeated/merged token headers and spoofed identity headers. Production has no in-memory session configuration.
Logout commits a PENDING sid intent before deleting the Redis session, then marks it REVOKED. Errors return HTTP 503, never success. Pending intents can be reconciled through RevocationCoordinator.recoverPending by a future controlled worker; no scheduler, HTTP recovery endpoint, Stream Relay or Agent pause propagation is included. A REVOKED row is a local fact and is not proof of downstream delivery. Repeated use of a revoked token returns 401.
H2 MySQL-mode HTTP tests use generated keys and Redis session-port substitutes; this is not MySQL, Redis, ACL, Gateway or end-to-end cross-service validation.
